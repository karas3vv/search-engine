# Сравнение BGE-M3, Tantivy и гибрида

Новый оценщик `habr_search.evaluation.compare` считает метрики трёх режимов на одних запросах и статьях. Старые команды оценки остаются рабочими. Корпус и индексы при проверке не изменяются.

## Разметка нескольких ответов

Один запрос может иметь несколько подходящих статей. В `relevant_article_ids` они перечисляются через `;`. Для степеней релевантности и дополнительных ответов используется отдельный CSV:

```csv
query_id,article_id,relevance,comment
question_1,795057,3,прямо решает поставленную задачу
question_1,888510,2,даёт полезный альтернативный способ
question_1,891074,0,другая задача
```

Оценки: `0` — не подходит, `1` — частично полезна, `2` — полезна, `3` — прямо отвечает. Для бинарных метрик релевантны все оценки больше нуля. Пустая ячейка означает «не проверено». Неизвестная статья и известная нерелевантная статья сохраняются раздельно, хотя при вычислении неизвестная временно считается нерелевантной.

Начальные положительные id из CSV запросов получают бинарную оценку `1`. Файл `--qrels` расширяет их; явная оценка `0` снимает ошибочную начальную метку. Исходные единицы не являются подтверждёнными оценками частичной полезности: при переходе к градациям их тоже нужно проверить и исправить.

У нынешнего benchmark статус `seed_labels_need_review`: обычно известна только одна подходящая статья. При такой разметке Recall@k совпадает с Hit@k, а AP совпадает с RR. Нельзя считать эти числа доказательством полноты поиска по всем полезным статьям. Новая программа помечает неполную разметку и сохраняет её покрытие в `metadata.csv`.

Для нескольких ответов можно начать с дополнительного `evaluation/queries_multirelevant.csv`: шесть запросов по трём темам, семь статей, от двух до четырёх начальных ответов на запрос. Градации и основания — `evaluation/qrels_multirelevant.csv`. Это небольшой диагностический dev-набор по документам Word, Power Platform и работе с Excel; он не является независимым holdout и не содержит исчерпывающей разметки корпуса.

## Таблица кандидатов без новых обращений к MWS

Из прежнего завершённого отчёта `evaluate_hybrid` можно получить объединение кандидатов всех трёх режимов. На текущем компьютере уже подготовлен файл `data/evaluation/judgments-dev-20261112.csv`: 1422 пары «запрос — статья», начальные метки помечены `seed_needs_review`.

Для другого отчёта или компьютера:

```bash
python -m habr_search.evaluation.prepare_judgments \
  --queries evaluation/benchmark_dev.csv \
  --report data/evaluation/ВАШ_ОТЧЁТ_HYBRID.csv \
  --output data/evaluation/judgments-dev.csv
```

Команда читает сохранённые кандидаты и корпус SQLite. MWS и Qdrant не нужны. Существующий output не перезаписывается. `--depth 5` позволяет начать с меньшего пула; по умолчанию глубина 20.

Проверяйте статью по содержанию вопроса, а не по общности темы или высокому score. Читайте полные тексты по ссылкам: показанный поиском отрывок может быть неудачным. У подходящих статей заполните `relevance`, у остальных поставьте `0`; для спорных случаев оставьте комментарий. У узкого вопроса действительно может быть только один правильный ответ — добавлять статьи ради количества нельзя. Пул также может пропустить полезные статьи: добавлять найденные вручную id разрешено.

## Какие метрики рассчитываются

Все показатели качества усредняются по запросам с хотя бы одной положительной меткой. Это macro-усреднение: каждый вопрос имеет одинаковый вес. Запросы без подходящего ответа учитываются отдельно через `negative_queries` и `negative_empty`.

| Метрика | Правило |
|---|---|
| MRR | среднее `1 / место первого релевантного результата` по полным сохранённым ранжированиям; пропуск даёт 0 |
| Precision | доля релевантных в фактически возвращённой выдаче первых `--top-k`; пустая выдача даёт 0 |
| Recall | найденные релевантные в первых `--top-k` / все известные релевантные |
| F1 | `2 * Precision * Recall / (Precision + Recall)` для каждого запроса, затем среднее |
| Precision@k | число релевантных в первых k / k; недостающие позиции не уменьшают знаменатель |
| Recall@k | число релевантных в первых k / все известные релевантные |
| F1@k | гармоническое среднее Precision@k и Recall@k для каждого запроса |
| MRR@k | первое подходящее место учитывается только в первых k |
| mAP | среднее AP: сумма Precision на местах релевантных статей / все известные релевантные |
| mAP@k | та же сумма до места k; знаменатель остаётся полным числом известных релевантных, как в `trec_eval map_cut` |
| nDCG@k | дисконтированная полезность, делённая на идеальную; `gain = 2**relevance - 1`, скидка `log2(место + 1)` |
| PR-AUC | площадь под PR-кривой по порогам score, рассчитанная трапециями отдельно для каждого запроса |
| Hit@k | доля запросов, для которых нашёлся хотя бы один подходящий результат в первых k |

На уровне одного запроса в `per_query.csv` записываются RR и AP; в `summary.csv` их средние называются MRR и mAP. Recall и Recall@top-k дублируют друг друга; Precision может отличаться от Precision@k, если реально найдено меньше k статей.

PR-AUC не подменяется AP/mAP. Одинаковые score проходят порог одновременно. У Tantivy документы без совпадений имеют score 0; у гибрида статьи вне объединения кандидатов имеют RRF 0. BGE-M3 получает оценки всех статей. Кривая строится по всему тому же корпусу и заканчивается Recall=1. Оценки разных движков и разных запросов в одну общую кривую не смешиваются.

Трапецеидальная PR-AUC может быть оптимистичной: если все документы имеют одну оценку, площадь равна `(1 + доля релевантных) / 2`. Это не означает, что пустая выдача хороша: её Precision, Recall, MRR и AP равны нулю. Для оценки поиска PR-AUC нужно рассматривать вместе с mAP и метриками @k, особенно при редких положительных метках.

Определения и выбранные соглашения: [trec_eval: AP@k](https://github.com/usnistgov/trec_eval/blob/master/m_map_cut.c), [scikit-learn: AP и отличие от трапеций](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html), [PR-кривая и пороги](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.precision_recall_curve.html).

## Получить новые ранжирования

Бесплатная проверка готовности, без запроса ключа и создания файлов:

```bash
python -m habr_search.evaluation.compare \
  --queries evaluation/queries_multirelevant.csv \
  --qrels evaluation/qrels_multirelevant.csv \
  --qdrant-url http://127.0.0.1:6333 --check-only
```

Для пробы на шести запросах:

```bash
python -m habr_search.evaluation.compare \
  --queries evaluation/queries_multirelevant.csv \
  --qrels evaluation/qrels_multirelevant.csv \
  --qdrant-url http://127.0.0.1:6333 \
  --output data/evaluation/comparison-multi-v1
```

Эта команда делает **шесть обращений к платному MWS**, по одному на запрос. Эмбеддинг переиспользуется для BGE-M3 и гибрида. Для основного dev-набора задайте `--queries evaluation/benchmark_dev.csv` и свой размеченный `--qrels`; там 40 запросов. Holdout проверяйте после выбора настроек и разметки, не используйте его для подбора параметров.

По умолчанию считаются k=1,3,5,10,20 и обычные Precision/Recall/F1 для выдачи из пяти результатов. Например, `--top-k 10 --cutoffs 5 10 20` меняет эти размеры без изменения корпуса. RRF использует по 20 кандидатов из каждого источника и веса 1:1; `--candidate-limit`, `--rrf-k`, `--dense-weight` и `--lexical-weight` задают другой эксперимент и сохраняются в контексте запуска.

Для полных MRR/mAP и PR-AUC получаются все векторные оценки статей и все лексические совпадения, без текстов и отрывков. Векторное ранжирование использует точное сравнение Qdrant; равные оценки источников упорядочиваются по id статьи. Гибрид ранжирует объединение своего ограниченного пула кандидатов с прежними правилами RRF. Полный расчёт не меняет лимиты веб-интерфейса. Старые отчёты с пятью результатами не содержат достаточных данных для полного MRR, mAP и PR-AUC.

В таблицах есть медиана и p95 **времени полного ранжирования**. Это не время веб-запроса: здесь другая глубина поиска, нет генерации отрывков и подсказок. С прежними замерами интерфейса эти значения напрямую не сравниваются.

При остановке повторите настройки и укажите папку запуска:

```bash
python -m habr_search.evaluation.compare \
  --queries evaluation/queries_multirelevant.csv \
  --qrels evaluation/qrels_multirelevant.csv \
  --qdrant-url http://127.0.0.1:6333 \
  --resume data/evaluation/comparison-multi-v1
```

Завершённые запросы повторно не отправляются. Несовместимая версия индекса, корпус, набор запросов, повреждённая строка или изменённые веса отклоняются. После сбоя API запрос автоматически не повторяется.

## Бесплатный пересчёт по расширенной разметке

```bash
python -m habr_search.evaluation.compare \
  --from-run data/evaluation/comparison-multi-v1 \
  --qrels evaluation/qrels_multirelevant.csv \
  --report-output data/evaluation/metrics-multi-v2
```

MWS, Qdrant и Tantivy не открываются. Можно менять разметку, top-k и cutoffs. Для других весов и кандидатов нужен отдельный запуск с соответствующим контекстом. Существующие таблицы не перезаписываются.

Папка запуска содержит небольшой `context.json` с параметрами, запросами и id корпуса, а также `rankings.csv` с исходными оценками. Это не копия текстов статей. В папке метрик:

- `summary.csv` — сводка по трём режимам и категориям;
- `per_query.csv` — метрики каждого запроса;
- `pr_curves.csv` — точки PR-кривых;
- `judgments.csv` — общий пул для следующего уточнения разметки;
- `metadata.csv` — параметры, версия индексов, соглашения формул и статус разметки.

Полные ранжирования позволяют добавлять релевантные статьи из того же корпуса в `--qrels` и пересчитывать метрики бесплатно. Для добавления самих статей в корпус потребуются новые согласованные индексы и новый запуск.

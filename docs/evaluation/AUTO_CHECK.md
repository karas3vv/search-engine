# Проверка auto на новых запросах

Правила маршрутизации `rules-v1` зафиксированы в коммите `e0331a3` до подготовки этого набора. Для нового эксперимента они не менялись.

## Набор

`evaluation/queries_auto.csv` содержит 24 запроса по восьми темам: ExecuteExcel4Macro, запуск VBA после обновления данных, OpenTelemetry/Yii2, ошибка публикации Xcode/TestFlight, nginx.exe/Vodka, cert-manager/FreeNS, диагностическое сообщение DKMS и общий deadline HTTP-клиента asyncio. У каждой темы три варианта: обозначение или сообщение ошибки, цитата/контекст и перефразирование. Есть обозначения только в теле статьи, чтобы проверить отказ от необоснованного включения гибрида.

Запросы подготовлены ассистентом по содержанию локального корпуса до получения новых выдач BGE-M3. `qrels_auto.csv` содержит по одному известному полезному ответу с основанием и хешем текста. Это **предварительные начальные метки, а не исчерпывающая разметка**. В такой начальной оценке AP совпадает с RR, а Recall@k с Hit@k; после прогона нужно проверить дополнительные статьи объединённого пула, прежде чем делать окончательный вывод о Precision, Recall и mAP.

Происхождение, число обращений и хеши файлов указаны в `evaluation/auto_cases_manifest.json`. Для скорости отдельно выбраны шесть запросов из шести тем в `queries_auto_latency.csv`; выбор сделан до результатов поиска. Запросов без ответа в этом наборе нет.

## Запуск одной командой

Из корня проекта, с установленными зависимостями и готовыми индексами:

```bash
./check_auto.sh
```

Скрипт запускает существующий Qdrant, бесплатно проверяет корпус и индексы, затем скрыто запрашивает ключ либо берёт `MWS_API_KEY`. Ключ остаётся в памяти процессов и не записывается в отчёт. Нужно **42 новых обращения к MWS**:

- 24 эмбеддинга для качества; один вектор запроса используется для всех вариантов ранжирования;
- 18 реальных HTTP-поисков: шесть запросов независимо выполняются в BGE-M3, hybrid и auto. У каждого свой свежий вызов MWS, поэтому его задержка включена в измерение.

Открытие индексов и ожидание готовности серверов не вызывают модель. Прогрева и автоматических повторов платного запроса нет. Существующие данные не переиндексируются.

Для заданной новой папки:

```bash
./check_auto.sh data/evaluation/auto-cases-v1
```

Скрипт не перезаписывает существующую папку. При сбое уже полученные полные ранжирования сохраняются в `comparison/`; их можно продолжить отдельной командой `evaluation.compare --resume <папка>/comparison` с теми же `--queries evaluation/queries_auto.csv`, `--qrels evaluation/qrels_auto.csv` и `--qdrant-url http://127.0.0.1:6333`. Завершённые запросы к модели повторяться не будут; неопределённая последняя попытка могла быть оплачена.

## Отчёты

- `comparison/` — полные выдачи трёх исходных режимов, контекст и объединённый пул `metrics-*/judgments.csv` для уточнения разметки.
- `quality/summary.csv` — сравнение качества BGE-M3, Tantivy, hybrid и auto.
- `quality/per_query.csv` — выбранный auto режим и причина решения для каждого запроса.
- `latency/requests.csv` — каждая попытка настоящего HTTP-запроса, время от клиента, серверное время, режим и статус Tantivy.
- `latency/summary.csv` — число измерений, медиана и p95 каждого режима.
- `latency/metadata.json` — параметры, хеш запросов и признак успешного завершения.

Сначала стоит посмотреть, на скольких вопросах включился гибрид и какие позиции изменились. Переключение само по себе не означает улучшение. Для него нужно сравнить метрики по той же проверенной разметке.

## Отдельный замер задержки

```bash
python -m habr_search.evaluation.benchmark_web \
  --queries evaluation/queries_auto_latency.csv --limit 0 --repeats 1 \
  --qdrant-url http://127.0.0.1:6333 --output data/evaluation/auto-latency-v1
```

Команда сама запускает три отдельных сервера на портах 8030–8032, дожидается `/api/health`, чередует порядок режимов и измеряет `/api/search` с `top_k=20`, как страница с «Показать ещё». Подсказки опечаток выключены одинаково у всех. Чужие процессы на занятых портах не завершаются; для других портов есть `--base-port`. Запущенные командой серверы завершаются при выходе, Qdrant остаётся работать.

`http_ms` включает передачу по loopback, серверную обработку и ожидание настоящего MWS. Это не браузерный рендеринг и не нагрузочный тест. MWS вызывается отдельно для каждого режима, поэтому на результаты влияет изменчивость сети и удалённого сервера. При шести измерениях p95 является максимумом; это первичный замер, а не надёжная оценка хвостовых задержек.

Для более устойчивого замера можно увеличить `--repeats`, но число обращений растёт как `число запросов × повторы × 3`. Например, шесть запросов и пять повторов — 90 обращений только для скорости. Если замер оборвался, файл попыток сохраняется и повтор не выполняется автоматически; папка для следующего замера должна быть новой.

## Уточнение разметки без новых обращений

После просмотра статей заполните объединённый `judgments.csv` и пересчитайте:

```bash
python -m habr_search.evaluation.evaluate_auto \
  --from-run data/evaluation/auto-cases-v1/comparison \
  --qrels /путь/к/проверенному/judgments.csv \
  --output data/evaluation/auto-cases-v1/quality-reviewed
```

Это не вызывает MWS. Для проверки правил нужны заголовки того же снимка Tantivy. Менять правила по результатам этого набора и затем выдавать оценку на нём за независимую нельзя.

Обычный `hybrid` использует веса 1:1, а `auto` при включении объединения — 4:1. Этот прогон сравнивает готовые режимы целиком; он не отделяет влияние весов от влияния маршрутизации. Правила и настройки зафиксированы до сбора новых выдач.

# LightGBM поверх BGE-M3 и Tantivy

`ltr` — отдельный экспериментальный режим с обученным порядком статей. BGE-M3 и Tantivy находят кандидатов параллельно, LightGBM локально ранжирует их объединение. Дополнительного вызова MWS для ранжирования нет: запрос всё так же получает один эмбеддинг BGE-M3.

## Запуск

```bash
python -m pip install -r requirements-ltr.txt
./run.sh --engine ltr --ranker-model data/ranker/lightgbm-v1
```

На текущем компьютере начальная модель уже обучена в `data/ranker/lightgbm-v1`. Внутри `model.txt` и `metadata.json`; оба файла нужны вместе. Они исключены из Git как остальные локальные данные. На другом компьютере перенесите папку вместе с соответствующими индексами и отчётами либо обучите модель заново.

Без флага основным остаётся BGE-M3. `hybrid` и прежний `auto` остаются базами сравнения. Отдельного нового фреймворка, сервера моделей или второго обученного ранжировщика нет.

## Признаки и порядок

Для каждой статьи вычисляются 16 признаков: косинусная оценка и позиция BGE-M3, BM25 и позиция Tantivy, флаги наличия источников, совпадения слов и точных обозначений в заголовке/тексте, покрытие с учётом редкости слов и длины текста/запроса. ID статьи и запроса не входят в модель.

По умолчанию используются первые 50 кандидатов каждого источника, максимум 100 разных статей. Эта глубина записана в артефакте и автоматически применяется сервером. Отсутствующая оценка источника обозначается нулём вместе с флагом отсутствия. Скрытого получения дополнительных семантических оценок для лексических кандидатов нет — офлайн и онлайн используются одинаковые признаки.

Текстовый каталог готовится из того же снимка Tantivy один раз при запуске. Он увеличивает время запуска и потребление памяти; повторного чтения корпуса для каждого запроса нет. Предсказание использует один CPU-поток. При равных оценках сохраняется приоритет порядка модели, затем Tantivy, затем id.

LightGBM учится с `lambdarank`, градациями 0–3 и gain `[0, 1, 3, 7]`. Итоговый `score` — сырая оценка ранжировщика, не вероятность и не косинусное сходство. В `diagnostics` выбранный путь обозначен `ltr`, записаны `ranker_model_sha256` и `ranker_ms` (признаки плюс предсказание). Отрывки строятся после ранжирования.

Поля весов и признаков правил прежнего `auto` для `ltr` не используются. На 120 локальных предсказаниях по сохранённым кандидатам признаки и LightGBM заняли около 2,1 мс по медиане и 3,2 мс по p95; это не время полного HTTP-поиска. Подготовка текстового каталога при запуске в этом замере заняла около пяти секунд.

## Обучение без новых эмбеддингов

```bash
python -m habr_search.evaluation.train_ltr \
  --from-run data/evaluation/comparison-multi-v1 \
  --qrels data/evaluation/judgments-preliminary-20261112.csv \
  --groups evaluation/ltr_topics.csv \
  --output data/ranker/lightgbm-next
```

Нужны сохранённые полные ранжирования, явные оценки и тот же снимок Tantivy. MWS и сервер Qdrant не вызываются. `--output` должен указывать новую папку; существующая модель не перезаписывается.

Неизвестные оценки **исключаются из обучения**, а не становятся нулями. Неявные исходные метки из CSV запросов тоже не используются: нужны оценки в `--qrels`. Запросы с одинаковыми оценками всех размеченных кандидатов не дают обучающих пар. Для этого начального протокола нужны минимум три темы и обучаемые группы каждого запроса.

`evaluation/ltr_topics.csv` относит две формулировки одной темы к одной группе. Проверка по очереди откладывает целую тему и обучается на остальных; параметры фиксированы, автоматического поиска параметров и подбора лучшего результата нет. В `validation/` сохраняются показатели предсказаний вне обучения. Затем серверная модель обучается на всех доступных размеченных группах. Нельзя выдавать её оценку на обучающих запросах за независимую проверку.

Начальная модель обучена на 221 паре из шести запросов и трёх близких тем. Разметка предварительная, подготовленная ассистентом. Статей без оценки и размеченных статей вне объединения кандидатов в обучении нет.

При проверке по темам модель BGE-M3 получила Precision@5 **0.8000**, MRR **0.8333**, nDCG@10 **0.7173**. LightGBM — соответственно **0.7667**, **0.9167**, **0.6692**. Результат смешанный, общего улучшения пока нет. Для надёжного обучения нужна более разнообразная проверенная разметка.

## Отдельная оценка

```bash
python -m habr_search.evaluation.evaluate_ltr \
  --from-run data/evaluation/auto-check-20261117-071449/comparison \
  --qrels evaluation/qrels_auto.csv \
  --model data/ranker/lightgbm-v1 \
  --output data/evaluation/ltr-new-check
```

Команда не обучает модель и не вызывает MWS. Использование того же исходного запуска, на котором модель обучалась, отклоняется. Отчёт сравнивает BGE-M3, Tantivy, RRF и LightGBM; RRF для этого сравнения пересчитывается с той же глубиной 50, поэтому может немного отличаться от прежних отчётов с глубиной 20.

В оценке неизвестные статьи по общему соглашению считаются нерелевантными; это ограничение метрик, а не правило обучения. Для PR-AUC отсутствующим результатам LightGBM назначается оценка ниже последнего кандидата. Отрицательные запросы не смешиваются с положительными в средних показателях качества.

На отдельном наборе из 24 запросов начальная модель сохранила MRR=1 и nDCG@10=1. В этом наборе пока по одному известному положительному ответу, поэтому эти числа не доказывают улучшение качества всей пятёрки. Новый режим не включён по умолчанию.

## Скорость и ошибки

Предельное дополнительное ожидание Tantivy, отсутствие очереди и возврат к модели при его ошибках сохраняются из `auto`. При ошибке предсказания или лексического сниппета также возвращается исходный порядок BGE-M3. Ошибки MWS/Qdrant не скрываются и не вызывают повторный платный поиск. Общая проверка индекса перед MWS переиспользуется, повторные get/count до получения эмбеддинга удалены; после поиска версия проверяется снова.

При запуске проверяются хеш модели, имена и версия признаков, коллекция, версии обоих индексов и глубина кандидатов. Несовместимый артефакт отклоняется до выполнения поиска. После изменения индексов нужно заново собрать модель из совместимых сохранённых результатов.

Для реального HTTP-замера четырёх режимов:

```bash
python -m habr_search.evaluation.benchmark_web \
  --queries evaluation/queries_auto_latency.csv --limit 0 --repeats 1 \
  --ranker-model data/ranker/lightgbm-v1 \
  --output data/evaluation/ltr-http-check
```

Это 24 новых вызова MWS: шесть запросов × четыре режима. Запускаются порты 8030–8033; чужие процессы не останавливаются. Локальное обучение и офлайн-предсказания не заменяют этот замер. При шести измерениях p95 остаётся описанием малого набора, а не надёжной оценкой под нагрузкой.

## Код

- `retrieval/ltr_features.py` — общие признаки обучения и сервера.
- `retrieval/ltr.py` — загрузка и предсказание единственной модели.
- `evaluation/ltr_data.py`, `train_ltr.py`, `evaluate_ltr.py` — группы, обучение и отдельная оценка; валидатор разметки переиспользуется.
- `retrieval/auto.py` и `web/app.py` — существующий параллельный поиск и API.
- `tests/test_ltr.py` — проверки разметки, разделения тем, артефакта, API и возврата к модели.

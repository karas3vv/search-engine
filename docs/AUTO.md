# Адаптивный поиск

При готовых Qdrant и Tantivy:

```bash
./run.sh --engine auto
```

Без флага основным остаётся BGE-M3. `auto` использует прежнюю коллекцию, токенизатор и снимок Tantivy; переиндексация не нужна. При запуске проверяются одинаковые множества id статей. После изменения корпуса оба индекса нужно обновить и перезапустить сервис.

## Как выполняется запрос

После проверки фразы локальный поиск Tantivy запускается в отдельном потоке. Одновременно основной поток один раз получает эмбеддинг MWS и ищет кандидатов в Qdrant. Маршрутизатор выбирает исходную выдачу модели либо взвешенное RRF. Сниппеты Tantivy строятся только для итоговых статей.

Эта версия **всегда вызывает MWS для допустимого поискового запроса**. Это выбор ранжирования после получения выдач; модель не пропускается. Дополнительная LLM для маршрутизации не используется.

## Правила `rules-v1`

По умолчанию сохраняются порядок, косинусные оценки и отрывки BGE-M3. Гибрид включается, если одновременно выполнены условия:

1. В запросе есть техническое обозначение (`ExecuteExcel4Macro`, `ERR_CONNECTION_RESET`, квалифицированное имя с разделителем) или фраза в кавычках.
2. Оно точно совпало с границами слов в заголовке первого результата Tantivy.
3. Не меньше 60% значимых слов запроса содержится в этом заголовке. Это буквальное сопоставление после нормализации регистра и `ё`, без морфологии.
4. Отрыв первого BM25 от второго составляет не меньше 10%: `(score1 - score2) / score1`. Единственный результат сравнивается с нулём. Это признак, а не вероятность релевантности.
5. Эта статья ещё не первая у модели.

Количество общих статей в первых пятёрках записывается для диагностики, но пока не влияет на решение. Правила не содержат конкретных контрольных запросов или id ответов. Нераспознанные обозначения остаются на семантическом пути.

Начальные параметры: веса BGE-M3:Tantivy **4:1**, `rrf-k=60`, по **20** кандидатов. Это проверяемая гипотеза, а не оптимум по независимой выборке.

```bash
./run.sh --engine auto --candidate-limit 20 \
  --dense-weight 4 --lexical-weight 1 --rrf-k 60 \
  --auto-lexical-wait-ms 5
```

У обычного `hybrid` прежние веса по умолчанию остаются 1:1. `min-score` и `spelling-db` для обоих режимов отклоняются; подсказки берутся из словаря Tantivy. Фраза меняется только при явном применении исправления пользователем.

## Ограничение ожидания

`--auto-lexical-wait-ms` ограничивает **дополнительное ожидание Tantivy после готовности модельной ветки**, по умолчанию 5 мс. Это не ограничение полного ответа: MWS, Qdrant, проверки индексов, планирование потоков и итоговые сниппеты требуют отдельного времени. При нулевом значении берётся только уже готовый локальный результат.

При задержке или ошибке Tantivy, включая ошибку его сниппетов, возвращается исходная выдача модели. Ошибки MWS и Qdrant не скрываются; повторного платного запроса нет.

Выполняющееся Rust-чтение нельзя безопасно прервать из Python. После тайм-аута оно может закончить работу, а следующий запрос временно использует модель, **не ставя новое локальное задание в очередь**. Старый результат не применяется к новой фразе. При остановке сервер дожидается текущего чтения и освобождает поток перед соединениями.

Как и раньше, один процесс обслуживает один поисковый запрос за раз; конкурирующий получает HTTP 429. Параллелизм двух веток не заменяет многопользовательское управление нагрузкой промышленного сервиса.

## Диагностика

В `/api/search` добавлено необязательное поле `diagnostics`:

- `decision.engine`, `decision.reason`, `decision.version`, `decision.features` — выбранный путь, причина, версия правил и признаки;
- `lexical_status` — `ready`, `timeout`, `busy` или `error`;
- `embedding_ms`, `qdrant_ms`, `lexical_ms`, `routing_ms`, `snippets_ms` — времена этапов;
- `dense_weight`, `lexical_weight`, `lexical_wait_ms` — параметры решения; в модельном пути лексический вес равен нулю.

`lexical_ms` равен `null`, если ветка не закончилась к моменту ответа. Времена параллельных этапов нельзя просто суммировать для получения `elapsed_ms`. Поле `score` содержит косинусную оценку при выборе модели и RRF при объединении; напрямую сравнивать их нельзя.

CLI выводит строки `auto_search` с решением, временами и агрегированными признаками. Исходная фраза, выделенные обозначения, ключ, тексты и векторы в журнал не записываются. Интерфейс служебные поля не показывает; они доступны в API и журнале.

## Бесплатная проверка качества

Для сохранённых полных ранжирований `evaluation.compare`:

```bash
python -m habr_search.evaluation.evaluate_auto \
  --from-run data/evaluation/comparison-multi-v1 \
  --qrels data/evaluation/judgments-preliminary-20261112.csv \
  --output data/evaluation/auto-check
```

Нужна новая папка `--output`. Команда читает заголовки из **той же версии Tantivy**, проверяет состав корпуса и не вызывает MWS или Qdrant. Сохраняет `summary.csv` для прежних трёх режимов и auto, `per_query.csv` с решениями и `metadata.json` с хешами, версией снимка и настройками. Доступны метрики @5 и @10, полный MRR, mAP и PR-AUC. Бинарная релевантность — оценка выше нуля, gain nDCG — `2^оценка - 1`; отрицательные запросы учитываются отдельно.

Проверка предполагает готовность Tantivy, не моделирует тайм-ауты и **не измеряет новую задержку**. В модельном пути сохраняется полное ранжирование; RRF располагает только выбранными кандидатами. Старые времена не выдаются за время auto.

17 ноября 2026 года на предварительном наборе из шести запросов auto выбрал BGE-M3 во всех случаях: Precision@5 **0.8000**, MRR **0.8333**, Recall@10 **0.6097**, nDCG@10 **0.7173**. Качество совпало с моделью; улучшение пока не подтверждено. Переключение на гибрид, параллельность, тайм-ауты, отсутствие очереди и ошибки проверяются автономными тестами.

До включения по умолчанию нужны отдельные запросы по новым темам, техническим обозначениям и перефразировкам, проверенная разметка и замеры медианы/p95 реального веб-поиска. Следует учитывать как средние метрики, так и ухудшения отдельных вопросов. Гарантии отсутствия регрессий на любых запросах нет.

## Код

- `habr_search/retrieval/router.py` — признаки и правила `rules-v1`.
- `habr_search/retrieval/auto.py` — параллельность, ожидание и диагностика.
- `habr_search/retrieval/tantivy_index.py` — кандидаты отдельно от сниппетов.
- `habr_search/web/app.py`, `AutoService` — прежний API и освобождение ресурсов.
- `habr_search/evaluation/evaluate_auto.py` — офлайн-проверка.
- `tests/test_auto.py` — автономные сценарии без настоящей модели.
